# Internationalization (i18n)

Animae is written in English and built to be translated. The engine repository ships **English only**; every other language arrives as a **locale pack** that an application, a game, or a translation package registers at startup. Nothing in the engine is specific to one language, script, or region.

This document covers:

- [the four locale settings](#the-four-locale-settings) and how they combine;
- [locale packs](#locale-packs): how to ship a translation of the engine, the CLI, the TUI, the host, and the web client;
- [authored content](#authored-content): string tables and content overlays for games and presets;
- [language-neutral runtime state](#language-neutral-runtime-state), [tooling](#tooling), and [record/replay](#recordreplay).

## The four locale settings

Animae separates four locale settings. All are BCP 47 tags and are configured independently.

| Setting | Config / API | Purpose |
|---|---|---|
| **UI locale** | `i18n.locale`, `createEngine({ i18n: { locale } })`, CLI `--lang`, env `ANIMAE_LOCALE`, web client `hello.locale` / `set_locale` | **Display strings** for humans: errors, CLI/TUI/web chrome, action labels, panel titles, achievement names, `$t:` string tables resolved at presentation time |
| **Prompt locale** | `i18n.promptLocale` | Language of the **static LLM prompt scaffolding** (appraisal, render, safety, memory, ...). Resolved from the `prompts` catalog of the registered locale packs; English when a pack lacks a section |
| **Output locale** | `i18n.outputLocale` (defaults to the UI locale) | Language the model must use for **player-facing** narration and dialogue; injected through a catalog message and `Intl.DisplayNames`. Takes precedence over `card.identity.language` and `world.language` unless a turn passes an explicit per-turn override |
| **Content locale** | `i18n.contentLocale` (defaults to the **prompt locale**, not the output locale) | **LLM-facing authored content** loaded from `locales/<locale>/` overlay trees: persona bodies, knowledge, templates, scene briefs, card text that is fed into prompts |

All four default to `en`. An explicit `i18n.contentLocale` in config wins over the prompt-locale default.

When the content locale is not the prompt locale (for example an English LLM layer in front of a game authored in another language), the **content overlay chain** falls back through the prompt locale after the requested tag, so a missing `locales/<content>/**` file still loads its `locales/<prompt>/**` mirror.

### Locale negotiation

Locale matching is generic and the same everywhere (`negotiateLocale`, `buildFallbackChain`, `matchAvailableLocale` in `@animae/i18n`):

1. the requested tag, then each less specific tag (`sr-Latn-RS` → `sr-Latn` → `sr`);
2. a catalog of the same language in a sibling variant (`pt-BR` asks, only `pt-PT` exists → `pt-PT`);
3. `en` as the last resort, never as a privileged language in product copy.

A key that the matched catalog lacks is looked up along the rest of the chain, ending in the English catalog, so a partial translation never shows a raw key.

## Locale packs

A **locale pack** is the translated resources of one locale:

```ts
import { registerLocalePack, type LocalePack } from "@animae/i18n";

export const frenchPack: LocalePack = {
  locale: "fr",
  catalogs: {
    errors: { config: { invalid: "La configuration est invalide." } },
    tui: { "command.desc.help": "Afficher l'aide" },
    prompts: { /* section id -> prompt text */ },
  },
};

// Call once at startup, before the engine, the CLI, or the server is created.
const unregister = registerLocalePack(frenchPack);
```

Rules of the registry (`packages/i18n/src/locale-packs.ts`):

- Packs live in a process-global registry. Every package that renders text reads the registry **at use time**, so a pack registered after a package was imported is still seen, and the prompt bundles are rebuilt when the registry changes (`localePacksVersion()`).
- **Packs may be partial.** Every key a pack does not translate falls back to the built-in English text, key by key.
- A catalog may be nested; nested objects are flattened to dotted keys (`{ command: { desc: { help } } }` is `command.desc.help`).
- When two packs provide the same locale and key, the one registered **later** wins. A pack for `en` overrides the built-in English text, which is how an application rewords product copy.
- `registerLocalePack` returns an unregister function; `registeredLocales(namespace?)` lists the locales that provide a namespace; `clearLocalePacks()` empties the registry (tests).

### Namespaces

A pack provides any of these catalogs (`LOCALE_NAMESPACES`):

| Namespace | Read by | Content |
|---|---|---|
| `errors` | `@animae/engine` | error messages by error code |
| `diagnostics` | `@animae/engine` | validation findings and warnings |
| `prompts` | `@animae/engine` | LLM-facing prompt text of the cognitive pipeline, flat `section id → text` |
| `gallery-prompts` | `@animae/engine` | LLM-facing prompt text of the CG gallery brief, flat `section id → text` |
| `cli` | `@animae/cli` | command-line help and messages |
| `tui` | `@animae/tui` | terminal UI chrome, command descriptions, tier and track labels |
| `host` | `@animae/host` | host stream and session text, `command.*`, `header.*`, `role.*` |
| `web` | `@animae/web` | web server and protocol messages |
| `web-client` | `@animae/web` | strings of the reference browser client, served as `locales/<tag>.json` |

The English catalogs under `packages/<pkg>/locales/en/*.json` (and `packages/engine/src/prompts/en/*.json` for prompts) are the **reference**: they define every key and every placeholder a translation has to cover.

### Prompts are translated text, not translated behavior

A `prompts` catalog contains the same section ids as the English bundle (`getPromptSection`, `promptLocales()`, `promptLocaleParityKeys(locale)` and `galleryPromptLocaleParityKeys(locale)` in `@animae/engine` expose them). Templates keep their `{placeholders}`. A locale without a section reads the English text, so a pack can translate the sections that matter first.

### Shipping a translation

A translation package is an ordinary workspace package that depends on `@animae/i18n` and exports a pack plus a registration helper:

```ts
// packages/locale-fr/src/index.ts
import { registerLocalePack, type LocalePack } from "@animae/i18n";
import errors from "./catalogs/errors.json" with { type: "json" };
import prompts from "./catalogs/prompts.json" with { type: "json" };

export const frenchPack: LocalePack = { locale: "fr", catalogs: { errors, prompts } };
export default frenchPack;
export const registerFrench = (): (() => void) => registerLocalePack(frenchPack);
```

The application imports it for its side effect (or calls `registerFrench()`) before it opens an engine. Check the pack against the English reference without starting anything:

```bash
animae i18n check --pack ./packages/locale-fr/src/index.ts
```

`--pack <module>` (repeatable) loads an ES module whose default export is `{ locale, catalogs }` and registers it before checking. `animae i18n check` compares every registered locale with English (missing keys, extra keys, placeholder mismatches, prompt sections) and exits non-zero on an error. With no pack registered it reports `English only` and succeeds.

### Web clients

The web server (`@animae/web`) serves UI locales to browsers:

- `GET /api/locales?locale=<tag>` lists the UI locales the server can serve, with display names rendered in `<tag>`.
- `GET /api/client-catalog?locale=<tag>` returns `{ locale, catalog }` with the flattened `web-client` strings of the closest registered locale (an empty catalog for English: the reference client carries its own English strings).
- The wire protocol negotiates per client: `hello.locale`, `hello_ok.locale` + `hello_ok.locales[]`, `set_locale`. See [the web protocol](../packages/web/docs/protocol.md).

## Authored content

Two content lanes, with different locale settings:

1. **LLM-facing content** is resolved from locale overlay trees `<root>/locales/<locale>/**` using the **content locale**. The model is told through the output locale which language to write player-visible text in.
2. **Display strings** are resolved from string tables (`strings/<locale>.yaml`, `locales/<locale>/strings.yaml`, `locales/<locale>/<name>.strings.yaml`, or package catalogs) using the **UI locale** of each viewer (each WebSocket client on the server). Authored YAML may use `$t:key`; loaders lift it to `{ i18n: { key } }` for **late binding**, so replay, rewind, and mid-session language switches never rewrite the timeline.

### Locale layers

Same machinery as [mods](./mods.md), but under `locales/<locale>/` at the data root:

- Full file replace: `locales/fr/world/locations/home.yaml`
- Patch: `locales/fr/world/locations/home.patch.yaml`
- String tables: `locales/fr/strings.yaml` with `$t: key` in authored YAML **display** fields (names, short descriptions, labels; not LLM prompt bodies)

**Overlay precedence:** the content locale chain lists the most preferred tag first. For each logical path the engine walks the chain and stops at the **first** locale that provides a full file, a `.patch.yaml`, or a `card.append.md` for that path. Later tags fill only paths the earlier tags did not touch; a fallback translation never overrides or merges on top of the preferred locale's file for the same path (`createLocaleOverlayStorage`).

String table keys are exactly the nested paths inside the files, flattened with dots; `locales/<tag>/<name>.strings.yaml` adds no prefix from the file name, so a table referenced as `$t:shop.title` has to nest `title` under `shop:`.

Validate completeness with `animae validate [--locale <uiLocale>]`: it applies the **content locale** overlays like the engine, resolves display `$t:` keys against the **UI locale** string tables, and fails on missing keys. `--locale` overrides config and `--lang` for that check only. Locale overlay and mod layered storage expose `locales/<tag>/*.strings.yaml` through `listFiles("locales/<tag>")` so validators see merged string tables.

Games should keep **structure-neutral base YAML** and put display text in locale layers or `$t:` tables.

### Preset display strings

Engine **presets** (see [presets](./presets.md)) may ship `locales/<tag>/strings.yaml`, embedded in the bundle as flat `displayStrings`. Policy `$t:dnd.check.*` (and similar) lift to `{ i18n: { key } }` at compile time; runtime merges tables along the preset `extends` chain (`collectPresetDisplayStrings`), with **later presets and game string tables overriding earlier keys** per locale. Hosts register the merged table under the `strings` i18n namespace for web snapshot localization; clients load the same tables so `set_locale` can re-bind without a round trip. Keys are flat paths (for example `dnd.check.perception_unusual`), not `web:`-prefixed: unresolved wire copy must never expose namespace markers to players.

A game or a translation package adds its own language to a preset by shipping `locales/<tag>/<name>.strings.yaml` next to its data; the preset's keys are the contract.

### Keeping replies in the output language

The working prompt, the persona, and the style examples usually stay in the content language while players read another. The engine keeps the model on the output language like this:

- **Per-turn language.** `scene.turn({ outputLocale })` applies to the player's reply **and** to the autonomous exchange that follows it, so a client's UI language never produces a reply in the engine default language.
- **Directive twice.** The static segment states the output language, and the closing user message repeats it in the output language itself.
- **Style examples are voice references.** When the output language differs from the content language, the heading of `identity.style_examples` says they are written in the content language and must not be reused in wording, script, or punctuation.
- **Name glossary.** Authors can provide `character.<id>.name` and `character.<id>.nickname` in the string tables of both languages. When the output locale differs from the content locale, the render prompt may list `content-language label → output-language spelling` for the speaker, addressee, and scene participants. The content-language side uses the card **nickname** string when the card defines one, otherwise the card **name**; the output side uses the same field from the output-locale table (`StringTableCache.lookup`, strict per locale, no cross-locale fallback). A player-chosen runtime alias is not rewritten in prompts (expansion uses card labels plus this optional glossary).
- **Names in UI text.** Name references (`{{name:<id>}}`) in text shown to a viewer, for example gallery titles, captions, and hints, use the same keys: for a viewer language other than the content language, pass `{ localizeNames: true }` to `Engine.display.resolve` so `character.<id>.nickname` (when the card has a nickname) or `character.<id>.name` of that language replaces the card label. A runtime alias (a name the player chose) always wins, and a language without its own spelling shows the card label. Prompts always use the card labels (with the optional cross-language glossary above).
- **Strict display lookup.** `Kernel.displayText.lookup(locale, key)` and `prepare([locale])` warm only that locale's string tables (plus preset tables for that tag). UI copy must not silently fall back to another language's spelling for name glossary rows; missing keys stay undefined and are omitted rather than shown as raw `$t:` markers (`prepareAuthoredProse` and prompt assembly drop undefined policy `$t:` the same way).
- **Late-bound policy strings.** Policy text written as `$t:key` (cue and event descriptions) is resolved in the **prompt** locale when it enters a prompt (`Kernel.displayText`; the engine loads the prompt, output, and content tables up front and the per-turn output tables at the start of a turn). A prompt never contains a raw `$t:` marker: a key that no table defines is dropped from the prompt (`animae validate` reports it).

## Language-neutral runtime state

- Timeline events and `EngineState` may carry `{ $t: key, params? }` or `{ i18n: { key, params? } }` instead of final copy.
- UIs call `localize(value, locale)`, `localizeDeep`, or `localizeSnapshot(state, t)` at presentation time.
- Web snapshots include both localized `text` / `label` and an optional `i18n: { key, params? }`, so clients can re-localize history after `set_locale`.
- Timeline events that surface human-readable copy include a **`systemMessage`** (`{ code, params?, namespace? }`) next to any legacy `message` string. UIs localize with `formatSystemMessage(msg, t)` from `@animae/engine` (or `engine.setUiLocale` plus the engine error catalogs). Example: `config.warning` carries `systemMessage: { code: "config.warning", namespace: "diagnostics", params: { code } }`.
- Entity id resolution (`resolveEntityRef`) uses `authoredFieldPlain`, so `$t:` / `{ i18n }` names do not break matching when the canonical id is supplied; localized name matching needs resolved display strings at the UI edge.

## `@animae/i18n`

The package has no dependency on the engine and is safe to use in a browser (`@animae/i18n/browser`, `@animae/i18n/react`).

```ts
import { createI18n, negotiateLocale, localizeError, localizeValue, localizeDeep } from "@animae/i18n";

const i18n = createI18n({
  locale: negotiateLocale({ env: process.env, explicit: "en" }),
  catalogs: { errors: { en: englishErrors, fr: frenchErrors } },
  defaultNamespace: "errors",
});

i18n.t("config.invalid");
i18n.t("errors:storage.path_escape", { path: ".." });

// Per request (web):
import { runWithLocale, scopedI18n } from "@animae/i18n";
runWithLocale(i18n.withLocale("de-DE"), () => handler());

// Inside the handler, process-wide translators re-bind to the request's locale:
scopedI18n(i18n).t("config.invalid"); // de-DE here, the process locale outside a request
```

- **Key resolution:** `ns:path` always selects namespace `ns`. A dotted key `a.b.c` is read as namespace `a` plus path `b.c` **only when `a` is a registered namespace**; otherwise the whole key is a path inside the default namespace (nested catalog groups such as `role.controller_lost` are never mistaken for namespaces). Pass `{ ns }` to `t()` to be explicit.
- **Catalogs:** `packages/<pkg>/locales/<locale>/*.json`: nested keys, an ICU subset (`{name}`, plural/select, `Intl` number/date/relative).
- **Fallback chain:** `buildFallbackChain(tag)` = tag, less specific tags, a same-language sibling that has a catalog, then `en`.
- **Pseudo-locale:** `xx-pseudo` or `en-XA` for QA (`applyPseudoLocale`): accents and padding that expose hard-coded or truncated strings.
- **Structured messages:** `{ code, params, namespace? }` for non-UI layers; format at the edge with `formatStructuredMessage`.
- **Errors:** `AnimaeError` plus `localizeError(err, i18n.t.bind(i18n))`; wire errors expose `code`, `params`, and a localized `message`.

### React (`@animae/i18n/react`)

Browser-safe bindings (no Node-only imports). Peer dependency: `react`.

```tsx
import { createI18n } from "@animae/i18n/browser";
import { I18nProvider, useT, useLocale, loadCatalogs } from "@animae/i18n/react";

const catalogs = loadCatalogs(import.meta.glob("./locales/**/*.json", { eager: true }));
const i18n = createI18n({ locale: "en", catalogs });

export function App() {
  return (
    <I18nProvider i18n={i18n}>
      <Toolbar />
    </I18nProvider>
  );
}

function Toolbar() {
  const t = useT();
  const [locale, setLocale] = useLocale();
  return (
    <>
      <span>{t("web:chrome.title")}</span>
      <button type="button" onClick={() => setLocale(locale === "en" ? "fr" : "en")}>
        {locale}
      </button>
    </>
  );
}
```

- `I18nProvider` accepts `i18n` or `translator` (`I18nInstance` from `createI18n`).
- `setLocale` calls `withLocale` and re-renders `useT` / `useLocale` subscribers.
- `loadCatalogs(modules)` merges eager glob maps keyed by `…/locales/<locale>/<namespace>.json`.

## `animae.yaml`

```yaml
i18n:
  locale: en           # UI / display strings
  promptLocale: en     # LLM scaffolding + default content locale
  outputLocale: en     # player-facing generation
  contentLocale: en    # optional override for authored overlays
  fallbackLocale: en
```

CLI: `animae --lang fr run`. TUI: `:lang fr`, which re-renders all chrome through `TuiI18nProvider`. A tag with no registered pack is accepted and falls back to English.

### TUI and host dynamic labels

Game-registered TUI chrome (`TuiAction.label`, `EntityTuiAction.label`, `SidePanelSection.title`, `CustomCommand.description`, prompt field labels) may be a plain string or a zero-argument getter `() => string` (`ResolvableText`). The shell resolves with `resolveText()` when rendering, so `:lang` updates toolbars, palettes, and panels without re-registering actions. Built-in colon command descriptions use catalog keys (`command.desc.*` in `packages/tui/locales/*/tui.json`) resolved at palette render time, not at module load.

Hygiene: `packages/tui/test/hygiene/no-hardcoded-ui-text.test.ts` blocks new English UI literals under `packages/tui/src`.

## Host and web

- Catalogs: `packages/host/locales/en/host.json` and `packages/web/locales/en/web.json`; other languages come from the `host` and `web` namespaces of registered packs.
- `SessionHost` stores system lines and errors as catalog keys / `LocalizableValue`; **`localizeSnapshot(state, t)`** (`packages/host/src/localize-snapshot.ts`) runs per client locale before web wire transfer.
- Resolution order for `$t:` / `{ i18n }` refs on the wire: `host:` keys for `header.*`, `command.*`, and `role.*`; then the preset **`strings`** namespace (merged from `collectPresetDisplayStrings` in `@animae/engine`); then `host:` again. Unresolved keys fall back to a title-cased tail: clients must not show raw `web:*` or `$t:` prefixes (the web client warns once if server copy still looks like a key).
- Transcript lines and action labels in snapshots get resolved **`text`** / **`label`** plus an optional **`i18n: { key, params? }`** for rebinding after `set_locale`. Games register toolbar actions with **`ResolvableText`** thunks (`string | () => string`, same as the TUI); `SessionHost.listActions()` resolves them in the viewer locale before the snapshot is sent (see [host](./modules/host.md)).
- Web protocol: the client `hello` carries an optional `locale`; `hello_ok` returns the negotiated `locale` and `locales[]`; the server also sends `locale { locale }`; `set_locale` triggers `locale`, `result`, and a fresh localized `snapshot`. Engine events and toasts forwarded to web clients are localized field by field in the requesting client's locale scope. See [the web protocol](../packages/web/docs/protocol.md).

### Host command API

Game colon commands receive `HostCommandApi` with:

- `locale(): string`: the viewer's UI locale;
- `t(key, params?)`: translate in the `host` namespace (and the merged engine error catalogs).

The surface matches the TUI `CommandApi` (`locale` / `t` are optional on both for backward compatibility). Built-in host colon commands store **`description` as catalog keys** (`command.desc.*` in `host.json`), not English literals in TypeScript.

## Migration guide (hosts)

1. **Split lanes.** Keep structural YAML neutral (ids, refs, mechanics). Put **display** copy in `locales/<uiLocale>/strings.yaml` and reference it with `$t:keys` on names, labels, descriptions, and achievement titles. Put **LLM-facing** prose (persona `card.md` bodies, knowledge docs, template guidance) under `locales/<contentLocale>/` overlay paths that mirror the base tree (`characters/<id>/card.md`, `world/knowledge/*.md`, ...). The default content locale follows the prompt locale; set `i18n.contentLocale` when the LLM layer is written in another language than the prompts.
2. **Runtime APIs.** Store timeline, panel, and system payloads as `LocalizedMessage` (`{ key, params?, ns? }`) or the lifted `{ i18n: { key, params? } }`. Resolve at the edge with `engine.display.resolve(value, { locale })`, `renderMessage(msg, t)`, or the host/web `localizeSnapshot`. Plain strings remain valid for generated narration (already localized by the model).
3. **Per-viewer UI.** Web: `hello.locale`, `set_locale`, the server `locale` ack, localized `snapshot` / `error` / `toast`. The controller's `outputLocale` for each turn is that client's UI locale (`submitInput(..., { outputLocale })` or `scene.turn({ outputLocale })`).
4. **Register translations before the engine opens.** Import the translation packages (or call their `register…` helpers) in the process entry point, ahead of `createEngine`, the CLI runner, or the web server.
5. **Validate.** `animae validate --locale <uiLocale>` checks `$t` tables for the UI lane and content files under `locales/<contentLocale>/` when any `locales/` tree exists; `animae i18n check` checks the registered packs.

### Minimal example (lantern village)

Fixture tested in `packages/engine/test/i18n/locale-layers-fixture.test.ts`:

```yaml
# world/locations/village.yaml (neutral structure)
id: village
name: $t:loc.village.name
summary: $t:loc.village.summary
```

```yaml
# locales/en/strings.yaml (display lane, UI locale)
loc:
  village:
    name: Lantern Village
    summary: Paper lanterns line the alleys.
```

```yaml
# locales/fr/world/locations/village.yaml (content lane, LLM overlay)
summary: |
  LLM-facing place brief in the content locale.
```

The engine load lifts `$t:` to `{ i18n: { key } }` for replay-safe state; `engine.display.resolve(location, { locale: "fr" })` resolves display keys without mutating stored events.

## Tooling

| Command | Purpose |
|---|---|
| `animae i18n check [--pack <module>]…` | Compare every registered locale with the English catalogs of the engine, TUI, CLI, host, and web: missing keys, extra keys, placeholder parity, prompt section parity |
| `animae i18n pseudo [text]` | Preview pseudo-localization |
| `animae validate [--locale <tag>]` | Check authored content: `$t:` keys, overlays, schema |

Repository tests keep the codebase locale-neutral: documentation is English only, source files hold no string literals in non-Latin scripts (those belong to catalogs and locale packs), and nothing points outside the repository.

## Record/replay

Recording keys include the **final prompt text**; changing the prompt locale or the output locale changes keys. Changing the **UI locale** alone does not alter timeline events or save slots: only localized presentation changes. Recording headers include the locale fields (see timeline recording metadata).
